# Chanlun-PRO 代码架构详解

本文是一份面向二次开发者的代码架构地图，重点解释项目如何把行情数据、缠论计算、Web 图表、回测、策略、选股、监控和实盘交易串起来。它不是安装手册，也不是缠论算法教程；安装配置细节请优先阅读 `配置文件说明.md`、`Windows安装文档.md`、`历史行情下载.md`、`策略编写与运行.md` 等专题文档。

## 1. 阅读导引

如果你刚接触这个项目，建议按下面顺序阅读源码：

1. 先看 `src/chanlun/cl_interface.py`，理解 K 线、分型、笔、线段、中枢、买卖点、背驰这些对象。
2. 再看 `src/chanlun/exchange/exchange.py` 和 `src/chanlun/exchange/__init__.py`，理解行情源如何被统一抽象。
3. 如果目标是改 Web 图表，重点看 `web/chanlun_chart/cl_app/__init__.py` 的 `/tv/history` 和 `web/chanlun_chart/cl_app/static/js/charts.js`。
4. 如果目标是写策略或回测，重点看 `src/chanlun/backtesting/base.py`、`backtest.py`、`backtest_klines.py`、`backtest_trader.py` 和 `src/chanlun/strategy/strategy_demo.py`。
5. 如果目标是接实盘，重点看 `src/chanlun/trader/online_market_datas.py`、各市场 `trader_*.py` 和 `script/trader/reboot_trader_*.py`。
6. 如果目标是批量任务，重点看 `script/crontab/`、`src/chanlun/xuangu/xuangu.py`、`src/chanlun/monitor.py`、`web/chanlun_chart/cl_app/alert_tasks.py`。

项目的一个核心原则是：行情来源可以不同，但最终尽量统一为 K 线 `DataFrame`，再进入 `cl.CL(...).process_klines(...)`，输出统一的缠论对象供 Web、策略、回测、选股和监控使用。

## 2. 项目整体分层

项目主线可以概括为：

```text
外部行情源 / 本地历史库
        ↓
Exchange 抽象层
        ↓
K线 DataFrame
        ↓
CL 缠论计算核心
        ↓
Web 图表 / Strategy / BackTest / Trader / Xuangu / Monitor
```

| 目录 | 职责 | 典型阅读入口 |
| --- | --- | --- |

### 2.2 核心数据流

项目中大多数业务最终都会走到这条链路：

```text
Exchange.klines(...)
  → pandas.DataFrame(date/open/high/low/close/volume/...)
  → cl.CL(code, frequency, cl_config)
  → process_klines(klines)
  → ICL 对象
  → get_bis()/get_xds()/get_bi_zss()/line_mmds()/line_bcs()
  → 图表绘制 / 策略信号 / 回测交易 / 监控提醒 / 选股结果
```

也就是说，Web、回测、监控、选股和实盘不是各自实现一套缠论逻辑，而是复用同一套 `CL` 与 `ICL` 对象模型。

### 2.3 架构上的几个边界

- 市场差异由 `Market` 和 `Exchange` 层吸收。
- 缠论结构由 `cl_interface.py` 定义，由 `cl.py` 计算。
- 策略不直接关心具体行情源，只通过 `MarketDatas` 读取数据。
- 策略不直接下单，只返回 `Operation`。
- Web 图表不直接计算缠论，而是调用后端 `/tv/history`，由后端返回扩展图形数据。
- 回测和实盘尽量复用策略逻辑，但使用不同的行情来源和交易执行器。

## 3. 核心领域模型

缠论计算结果不是简单的指标数组，而是一组层次化对象。理解这些对象，是理解 Web 标注、策略、选股和监控的前提。

### 3.1 Market：市场统一标识

`Market` 定义在 `src/chanlun/base.py:4`，是多市场适配的基础。它覆盖 A 股、港股、国内期货、纽约期货、数字货币合约、数字货币现货、美股和外汇。

`Market` 会影响：

- `get_exchange(Market)` 创建哪种行情源。
- Web 页面支持哪些市场和默认标的。
- 回测配置中的 `market`。
- 数据库存储和 K 线表命名。
- 脚本同步哪个市场的数据。

### 3.2 Config：缠论规则配置集合

`Config` 定义在 `src/chanlun/cl_interface.py:18`。它不是运行配置文件，而是缠论计算规则的枚举集合，覆盖：

- K 线类型：普通 K 线、缠论 K 线。
- 缺口定义。
- 分型区域、分型区间、分型包含关系。
- 笔类型、笔标准化、笔区间。
- 线段区间、笔破坏规则。
- 走势段区间。
- 中枢类型、中枢区间、中枢重叠区间和中枢位置关系。

这些配置最终通过 `cl_config` 影响 `cl.CL(..., config)` 的计算结果。同一份 K 线，在不同 `cl_config` 下可能得到不同的笔、线段、中枢、买卖点和背驰。

### 3.3 Kline 与 CLKline

`Kline` 定义在 `src/chanlun/cl_interface.py:87`，表示原始 K 线，主要字段包括：

- `index`
- `date`
- `h/l/o/c`
- `a`

`CLKline` 定义在 `src/chanlun/cl_interface.py:114`，表示处理包含关系后的缠论 K 线，主要字段包括：

- `k_index`：对应原始 K 线位置。
- `date`
- `h/l/o/c/a`
- `klines`：该缠论 K 线包含的原始 K 线列表。
- `n`：包含 K 线数量。
- `q`：是否存在缺口。
- `up_qs`：合并时的前序趋势。

基础关系是：

```text
原始 K 线 Kline
        ↓ 包含关系处理
缠论 K 线 CLKline
```

后续分型、笔、线段都建立在 `CLKline` 之上。

### 3.4 FX、LINE、BI、XD

`FX` 定义在 `src/chanlun/cl_interface.py:152`，表示顶分型或底分型。它保存分型类型、分型中间 K 线、构成分型的 K 线列表、分型值和完成状态。

`LINE` 定义在 `src/chanlun/cl_interface.py:293`，是线型结构基类，`BI` 和 `XD` 都继承它。它抽象了：

- `start` / `end` 分型。
- 高低点。
- 方向：`up` 或 `down`。
- 索引。
- 力度、角度、顶底取值等通用能力。

`BI` 定义在 `src/chanlun/cl_interface.py:545`，表示笔。笔可以挂载：

- `mmds`：买卖点。
- `bcs`：背驰。
- `zs_type_mmds`：按中枢类型归类的买卖点。
- `zs_type_bcs`：按中枢类型归类的背驰。

`XD` 定义在 `src/chanlun/cl_interface.py:809`，表示线段。线段由更低级别线型构成，也可以挂载买卖点和背驰，并维护特征序列、完成状态、是否拆分等信息。

对象层级：

```text
CLKline → FX → BI → XD
```

### 3.5 ZS、MMD、BC

`ZS` 定义在 `src/chanlun/cl_interface.py:350`，表示中枢。它保存中枢类型、起止线、构成线段、`zg/zd/gg/dd`、方向、级别、完成状态等。

`MMD` 定义在 `src/chanlun/cl_interface.py:504`，表示买卖点，例如 `1buy`、`2buy`、`3sell` 等。它会挂载相关中枢和提示信息。

`BC` 定义在 `src/chanlun/cl_interface.py:518`，表示背驰。它保存背驰类型、关联中枢、比较线、比较线集合和背驰结果。

它们之间的关系可以理解为：

```text
BI / XD 形成 ZS
BI / XD 上挂载 MMD 和 BC
Strategy / Monitor / Web 图表读取这些标记
```

### 3.6 ICL：外部读取缠论结果的统一接口

`ICL` 定义在 `src/chanlun/cl_interface.py:1089`，是 `CL` 应实现的抽象接口。外部模块通常不应该依赖 `CL` 内部细节，而应通过 `ICL` 访问结果。

常用读取方法包括：

- `get_code()`
- `get_frequency()`
- `get_config()`
- `get_src_klines()`
- `get_klines()`
- `get_cl_klines()`
- `get_fxs()`
- `get_bis()`
- `get_xds()`
- `get_zsds()`
- `get_qsds()`
- `get_bi_zss()`
- `get_xd_zss()`
- `get_last_bi_zs()`
- `get_last_xd_zs()`

完整对象流转图：

```text
Kline
  → CLKline
  → FX
  → BI
  → XD
  → ZS / ZSD / QSD
  → MMD / BC
  → Web 标注、策略信号、选股结果、监控提醒
```

## 4. 缠论计算核心与增量模型

### 4.1 CL 的定位

`src/chanlun/cl.py` 是缠论核心计算入口，外部代码大量通过 `from chanlun import cl` 后调用 `cl.CL(code, frequency, cl_config)`。

同目录下可能存在 `cl-原版.py`、`cl-加密.py` 等文件。架构理解上可以用它们辅助观察方法轮廓，但不应把反编译文件当作权威源码逐行解释。对外稳定边界应以 `cl_interface.py` 定义的对象和 `ICL` 接口为准。

### 4.2 增量计算

项目 README 和代码设计都强调逐 Bar 增量处理。核心入口是：

```text
cl.CL(...).process_klines(klines)
```

它的架构意义是：

- 可以重复喂入新的 K 线数据。
- 已处理过的历史数据尽量跳过。
- 最后一根 Bar 会根据最新行情更新。
- 未确认结构可能随新 K 线变化。
- 已确认结构通常可以稳定复用。

这个模型支撑了几个关键场景：

| 场景 | 为什么依赖增量计算 |
| --- | --- |
| Web 图表 | 页面刷新或行情更新时，不希望每次全量重算所有缠论结构 |
| 监控提醒 | 定时任务频繁扫描多个标的和周期，需要降低重复计算成本 |
| 回测 | 回测按时间推进，如果每一步全量计算会非常慢 |
| 实盘交易 | 实盘循环运行策略，需要快速更新当前缠论结构 |
| 选股 | 批量标的扫描时，缓存和增量计算能显著降低耗时 |

### 4.3 计算管线

从架构角度，可以把 `CL` 的计算理解为：

```text
pandas.DataFrame K线
  → 标准化为 Kline 对象
  → 处理包含关系，形成 CLKline
  → 识别顶/底分型 FX
  → 由分型生成笔 BI
  → 由笔生成线段 XD
  → 由笔/线段生成中枢 ZS、走势段 ZSD、趋势段 QSD
  → 计算力度、背驰 BC、买卖点 MMD
  → 暴露为 ICL 可读取结果
```

外部模块不需要知道每一步内部算法细节，只需要知道如何喂入 K 线，以及如何通过 `ICL` 读取结果。

### 4.4 工具层关系

`src/chanlun/cl_utils.py` 是 Web、图表、配置和部分分析逻辑的重要工具层。关键函数包括：

- `web_batch_get_cl_datas`：Web/监控/AI 等批量获取缠论数据入口，定义在 `src/chanlun/cl_utils.py:13`。
- `query_cl_chart_config`：读取市场和代码的图表缠论配置，定义在 `src/chanlun/cl_utils.py:283`。
- `cl_data_to_tv_chart`：把 `ICL` 对象转换成 TradingView 图表数据，定义在 `src/chanlun/cl_utils.py:640`。

`src/chanlun/file_db.py` 的 `FileCacheDB` 定义在 `src/chanlun/file_db.py:21`，负责文件缓存 K 线、Web 缠论计算对象和部分 pickle 状态。Web 场景中的缓存链路通常是：

```text
web_batch_get_cl_datas
  → FileCacheDB.get_web_cl_data
  → 读取已有 ICL 缓存
  → 判断配置和 K 线是否变化
  → 必要时新建 cl.CL
  → process_klines 增量更新
  → 写回缓存
```

`src/chanlun/cl_analyse.py` 则更偏高级分析，例如多级别走势分析、线形态分析等，属于建立在 `ICL` 和 `cl_interface` 对象模型之上的二次分析层。

## 5. Exchange 行情与交易所适配层

### 5.1 Exchange 抽象接口

`Exchange` 定义在 `src/chanlun/exchange/exchange.py:35`，统一抽象行情和交易相关能力。

核心方法包括：

- `default_code()`：默认标的。
- `support_frequencys()`：支持的 K 线周期。
- `all_stocks()`：全部标的。
- `now_trading()`：是否交易中。
- `klines(code, frequency, start_date=None, end_date=None, args=None)`：获取 K 线。
- `ticks(codes)`：获取实时 tick。
- `stock_info(code)`：标的信息。
- `stock_owner_plate(code)`：所属板块。
- `plate_stocks(code)`：板块成分。
- `balance()`：账户资金。
- `positions(code="")`：持仓。
- `order(code, o_type, amount, args=None)`：下单。

不是每个实现都完整支持交易能力。有些 exchange 只适合作为行情源，账户和下单方法可能不可用或仅用于特定市场。

### 5.2 get_exchange 工厂

`get_exchange` 定义在 `src/chanlun/exchange/__init__.py:9`，负责把 `Market` 转换成具体 `Exchange` 实例。

调用关系：

```text
Market.A / Market.HK / Market.US / ...
  → get_exchange(market)
  → 读取 config.EXCHANGE_*
  → 创建具体 Exchange 子类
  → 缓存到全局 g_exchange_obj
  → Web / 回测 / 脚本 / 监控复用
```

典型配置项来自 `src/chanlun/config.py.demo`：

| 市场 | 配置项 | 常见实现 |
| --- | --- | --- |
| A 股 | `EXCHANGE_A` | `tdx`、`futu`、`baostock`、`db`、`qmt` |
| 港股 | `EXCHANGE_HK` | `tdx_hk`、`futu`、`db` |
| 国内期货 | `EXCHANGE_FUTURES` | `tq`、`tdx_futures`、`db` |
| 纽约期货 | `EXCHANGE_NY_FUTURES` | `tdx_ny_futures`、`db` |
| 外汇 | `EXCHANGE_FX` | `tdx_fx`、`db` |
| 数字货币合约 | `EXCHANGE_CURRENCY` | `binance`、`db` |
| 数字货币现货 | `EXCHANGE_CURRENCY_SPOT` | `binance_spot`、`db` |
| 美股 | `EXCHANGE_US` | `alpaca`、`polygon`、`ib`、`tdx_us`、`db` |

### 5.3 多市场周期转换

`src/chanlun/exchange/exchange.py` 中还包含多市场 K 线周期转换函数。这个设计很重要，因为不同市场的时间规则不同：

- A 股有午休和收盘时间。
- 期货有日盘、夜盘和不同品种交易时段。
- 数字货币是 24 小时交易。
- 美股和纽约期货涉及不同时区和交易日。

因此，项目中的周期转换不是简单 `resample`，而是和市场交易时间紧密相关。回测时 `BackTestKlines` 也会动态合成高周期 K 线，以降低未来函数风险。

### 5.4 ExchangeDB：本地历史库适配

`ExchangeDB` 定义在 `src/chanlun/exchange/exchange_db.py:21`，是本地数据库行情适配层。它实现 `Exchange` 接口，用于从本地历史库读取 K 线。

典型使用场景：

- 回测：`BackTestKlines` 从 `ExchangeDB` 取历史行情。
- 历史选股回放：按历史时间推进并计算信号。
- 离线分析：不依赖实时行情接口。

数据通常由 `script/crontab/reboot_sync_*_klines.py` 系列脚本同步到本地库。

### 5.5 新增数据源的入口

如果要新增一个行情源，通常需要：

1. 新建或修改 `src/chanlun/exchange/exchange_*.py`，实现 `Exchange` 子类。
2. 至少实现 `default_code()`、`support_frequencys()`、`all_stocks()`、`now_trading()`、`klines()`。
3. 如果要支持实盘，还要实现 `ticks()`、`balance()`、`positions()`、`order()` 等。
4. 在 `src/chanlun/exchange/__init__.py` 的 `get_exchange` 中接入。
5. 在 `src/chanlun/config.py.demo` 中增加或说明配置项。
6. 检查 Web 市场周期、默认代码、搜索和标的信息是否可用。
7. 如需回测，补充历史数据同步脚本或写入 `ExchangeDB` 的流程。

## 6. Web 架构：Flask、Tornado、TradingView UDF

### 6.1 启动链路

Web 主入口是 `web/chanlun_chart/app.py`。启动时它会：

1. 将仓库 `src` 目录加入 `sys.path`。
2. 将 Web 目录加入 `sys.path`。
3. 导入 `chanlun.config`。
4. 导入 `cl_app.create_app`。
5. 创建 Flask app。
6. 用 Tornado `WSGIContainer` 和 `HTTPServer` 包装 Flask。
7. 监听 `config.WEB_HOST:9900`。
8. 默认打开浏览器访问 `http://127.0.0.1:9900`，传入 `nobrowser` 时不自动打开。

链路：

```text
windows_run.bat / uv run web/chanlun_chart/app.py
  → web/chanlun_chart/app.py
  → create_app()
  → Flask app
```

## 7. 回测架构

回测框架位于 `src/chanlun/backtesting/`，核心设计是把“行情推进”“策略判断”“交易执行”拆开。

### 7.1 核心对象

| 对象 | 定义位置 | 职责 |
| --- | --- | --- |
| `POSITION` | `src/chanlun/backtesting/base.py:16` | 持仓对象，记录开仓、平仓、盈亏、最大浮盈浮亏等 |
| `Operation` | `src/chanlun/backtesting/base.py:117` | 策略返回的操作指令，包括开平仓、买卖方向、买卖点、止损、仓位比例等 |
| `MarketDatas` | `src/chanlun/backtesting/base.py:165` | 策略读取行情和缠论数据的统一接口 |
| `Trader` | `src/chanlun/backtesting/base.py:214` | 交易执行抽象接口 |
| `Strategy` | `src/chanlun/backtesting/base.py:245` | 策略基类，要求实现 `open` 和 `close` |
| `BackTest` | `src/chanlun/backtesting/backtest.py:38` | 回测编排器 |

### 7.2 BackTest 编排流程

`BackTest` 负责组合数据、策略和交易执行器。典型配置包含：

- `mode`
- `market`
- `base_code`
- `codes`
- `frequencys`
- `start_datetime`
- `end_datetime`
- `init_balance`
- `fee_rate`
- `max_pos`
- `cl_config`
- `strategy`

主流程：

```text
BackTest(config)
  → 创建 Strategy
  → 创建 BackTestKlines
  → 创建 BackTestTrader
  → datas.init(base_code, next_frequency)
  → while datas.next(next_frequency)
      → trader.update_position_record()
      → for code in codes
          → trader.run(code)
          → strategy.close(...)
          → strategy.open(...)
          → trader.execute(Operation)
  → trader.end()
  → 输出持仓、订单、收益、图表等结果
```

### 7.3 BackTestKlines 与防未来函数

`BackTestKlines` 是回测里非常关键的一层。它不是简单返回完整历史 K 线，而是维护当前回测时间 `now_date`，让策略只能看到当前时间点之前应该可见的数据。

它的职责包括：

- 从 `ExchangeDB` 加载历史 K 线。
- 按基础标的和基础周期推进回测时间。
- 根据 `now_date` 截断每个标的、每个周期的数据。
- 通过 `get_cl_data(code, frequency, cl_config)` 创建或更新当前可见的 `ICL`。
- 在需要时用低周期合成高周期，避免直接使用未来尚未完成的大周期 K 线。

因此，策略在回测中应该通过 `market_data.get_cl_data(...)` 读取数据，而不是绕过 `BackTestKlines` 去读全量历史行情。

### 7.4 BackTestTrader 执行顺序

`BackTestTrader` 负责模拟交易，它会：

1. 遍历当前持仓，先调用策略 `close` 判断是否平仓。
2. 执行平仓 `Operation`。
3. 调用策略 `open` 判断是否开仓。
4. 执行开仓 `Operation` 或放入缓冲。
5. 更新持仓、订单、手续费和收益。
6. 清理数量为 0 的持仓。

典型顺序：

```text
BackTestTrader.run(code)
  → strategy.close(...)
  → execute(close Operation)
  → strategy.open(...)
  → execute(open Operation)
  → update positions/orders/balance
```

### 7.5 Strategy 与 Operation

策略开发者主要关心 `Strategy.open` 和 `Strategy.close`：

```text
Strategy.open(code, market_data, poss)
Strategy.close(code, mmd, pos, market_data)
```

策略不直接下单，而是返回 `Operation`。交易执行器根据 `Operation` 决定如何开仓、平仓、记录订单或真实下单。

以 `src/chanlun/strategy/strategy_demo.py:7` 的 `StrategyDemo` 为例，策略通常会：

1. 调用 `market_data.get_cl_data(code, frequency)`。
2. 读取 `cd.get_bis()`、`cd.get_xds()`、`cd.get_bi_zss()` 等结构。
3. 判断买卖点、背驰、停顿、止损等条件。
4. 返回 `Operation` 或 `None`。

常见业务数据包括：

- 监控任务和监控记录。
- TradingView 图表布局。
- TradingView 手工绘图。
- 图表 marks。
- 订单记录。
- AI 分析记录。
- 通用缓存。

### 10.3 K 线历史库

本地历史库一般通过 `ExchangeDB` 读取。数据写入通常来自 `script/crontab/reboot_sync_*_klines.py` 系列脚本。

典型同步链路：

```text

  → 创建 ExchangeDB(market)
```

### 10.4 FileCacheDB

`FileCacheDB` 定义在 `src/chanlun/file_db.py:21`，主要职责：

- 缓存行情数据。
- 缓存 Web 缠论计算对象。
- 缓存 pickle 状态。
- 缓存低周期合成高周期相关数据。

Web 缠论缓存非常关键：

```text
market + code + frequency + cl_config hash
  → 缓存文件 key
  → 读取已有 ICL
  → 检查 K 线连续性和最新数据是否变化
  → 有效则增量更新
  → 无效则重新创建 CL
```

## 14. 架构约束与易错点

### 14.1 不要绕过 Exchange

如果在 Web、策略或脚本中直接写死某个第三方行情接口，会破坏多市场抽象。新增数据源应优先通过 `Exchange` 子类接入。

### 14.2 策略不要直接下单

策略应返回 `Operation`，由 `BackTestTrader` 或实盘 Trader 执行。这样同一个策略才能同时用于回测和实盘。

### 14.3 回测必须防未来函数

回测中不能直接读取完整历史行情做判断。策略应通过 `BackTestKlines` 暴露的 `MarketDatas.get_cl_data()` 获取当前时间点可见数据。

### 14.4 TradingView UDF 格式不能随意改

`/tv/config`、`/tv/symbols`、`/tv/search`、`/tv/history` 等接口要符合 TradingView UDF 预期。项目在 `/tv/history` 中扩展了缠论字段，前端 `charts.js` 也依赖这些字段。

### 14.5 未确认信号可能变化

缠论计算支持增量更新，最后一根 K 线会变化。未确认买卖点、背驰、线段等结构可能随新 K 线消失或变化。策略和监控要区分已完成结构和未完成结构。

### 14.6 不要把反编译文件当权威源码

`cl-原版.py` 可辅助理解方法轮廓，但架构文档和开发应以当前可维护入口、接口定义和实际运行调用为准。

### 14.7 配置文件不随仓库提交

`src/chanlun/config.py` 需要从 `src/chanlun/config.py.demo` 复制生成，并被 `.gitignore` 排除。代码和文档不能假设真实配置一定存在。

### 14.8 授权文件会影响功能

`check_env.py` 和 `windows_run.bat` 会检查 `src/pyarmor_runtime_005445/pyarmor.rkey`。缺少授权文件时，部分缠论核心功能可能降级或不可用。

### 14.9 PM2 配置可能有历史遗留

`script/chanlun_web.config.js` 等 PM2 配置可能指向旧 Web 路径或旧启动方式。当前主 Web 入口应以 `web/chanlun_chart/app.py` 为准。

## 16. 总结

Chanlun-PRO 的核心架构可以压缩成一句话：用 `Exchange` 抹平多市场行情差异，用 `CL` 增量计算缠论结构，用 `ICL` 暴露统一结果，再由 Web、回测、策略、实盘、选股和监控分别消费这些结果。

理解这个主线后，二次开发时就可以按目标定位：

- 行情源问题看 `exchange/`。
- 缠论对象看 `cl_interface.py`。
- 缠论图表看 `/tv/history` 和 `charts.js`。
- 策略逻辑看 `Strategy` 和 `Operation`。
- 回测推进看 `BackTestKlines`。
- 实盘执行看各市场 `Trader`。
- 批量任务看 `script/crontab/` 和 Web task 类。
- 缓存和持久化看 `FileCacheDB`、`db.py`、`ExchangeDB`。
