1. 审计范围与结论摘要

仓库当前不是单一 Web 项目，而是一个以多市场行情为核心、同时承载 TradingView 图表、数据同步、策略监控、选股和离线回测的 Python 工作区。Web 只是其中一个运行面。

8MarketRegistry 注册市场：A、HK、FX、US、国内期货、纽约期货、合约币、现货币
2024web 目录受版本控制文件数，主要体量来自 TradingView JavaScript bundle 和 CSS
91tests/ 测试文件，包含领域、Web、Provider、质量门禁和删除能力防回归
体量工作树大小会受 .venv、linked worktree、缓存和未跟踪文件影响；清理判断不使用不可复现的单一数字
重要边界：本文最初由只读架构审计生成，随后在 2026-08-17 文档刷新中同步 README、活动文档和示例配置注释。产品运行逻辑、锁文件、测试、archive 和 audit 原始证据未改；ECharts 删除是文档刷新前已存在的工作树变更。

核心判断

  • 当前架构的组合根是 web/tradingview_zy_chart/cl_app/__init__.py:create_app，它把安全、数据库、市场元数据、缓存、任务服务和蓝图组装成一个 Flask 应用。
  • Provider 路由的单一事实来源是 src/tradingview_zy/market_registry.py。标准工厂先解析市场和配置，再在 import、构造和缓存发布之前执行已移除 Provider 的 tombstone 检查。
  • Web 进程和 APScheduler 进程是两个明确的所有权域。Web 保存任务配置并读取状态快照，只有独立 scheduler 进程执行监控任务。
  • 实盘下单不是当前支持能力。Exchange.order() 和取消入口 fail-closed，回测的 Operation 不能被解释成券商订单。
  • 没有证据证明当前测试套件整体过时。完整本地回归通过，专用环境的 MySQL/Chromium 测试按环境变量设计性跳过。

3. 模块协调与关键接口

3.1 组合根与依赖注入

create_app() 在 web/tradingview_zy_chart/cl_app/__init__.py:37 完成以下工作：检查非回环监听必须有登录凭据，解析会话密钥和 CSRF 信任源，创建 Tick 限流器与 Provider 并发门，建立 HistoryRequestTracker 和状态存储，生成市场静态元数据，惰性注册 AlertTasks/XuanguTasks，执行 TradingView 存储迁移，然后把依赖装入不可变的 WebAppServices。

蓝图通过 get_web_services() 读取容器，不直接从全局配置构造第三方对象。这样做的价值是：应用 factory 可被测试重复创建，Provider 和 APScheduler 不会因为只访问首页而启动网络线程。

3.2 MarketRegistry → Provider facade

  1. 路由或任务把字符串市场解析成 Market，入口在 src/tradingview_zy/market_registry.py:572 附近。
  2. selected_provider() 按 MARKET_PROVIDERS、旧配置属性、descriptor 默认值的顺序选择 Provider，但不 import SDK。
  3. get_exchange() 在 src/tradingview_zy/exchange/__init__.py:58 先执行已移除 CTP/ZB 的 tombstone，再加锁检查缓存、读取 ProviderSpec、动态导入并构造适配器。
  4. ContractedExchange 在构造时验证声明能力对应的方法不是继承自宽泛基类的空桩；调用时检查 capability、转换异常并验证响应类型。
  5. 只有完整构造且能力检查通过的 facade 才进入 g_exchange_obj。关闭或切换 provider 时先关闭旧对象，再清除缓存。

3.3 数据边界

Provider → canonical K 线

web_payloads.prepare_klines_for_market() 深拷贝 DataFrame，绑定 code/frequency，按市场时区本地化 naive 时间，拒绝重复或非递增时间、缺列、非有限数值、负 volume 和不一致 OHLC。它是 UDF 和策略输入的防腐层。

Strategy → BatchRunResult

strategies/base.py 将策略输出限制为 StrategySignal 或有限 list，并按 Selection/Monitoring purpose 检查动作集合、目标身份、时间、消息和 metadata。批次显式区分 hits、misses、failures。

Web → DB

tv_storage.py 按 UTF-8 字节限制图表、模板、绘图字段，并以认证主体绑定 owner；db.py 在同一事务内执行配额、唯一性和迁移逻辑。

Signal → Operation

strategy_bridge.py 只接受带明确 metadata.trade 的可执行监控信号，产生带快照的 TradeDecision/Operation。桥接不绕过 live-trading-disabled 边界。

5. 运行链路

5.1 安装与 Web 启动

  1. 使用 Python 3.11 和 uv 0.10.0，执行 uv sync --locked。pyproject.toml 声明依赖，uv.lock 决定安装结果，package/ 提供平台 wheel。
  2. 复制 src/tradingview_zy/config.py.demo 为私有 config.py。凭据字段保存 env://、managed://、file:// 或 keyring:// 引用，不把 Secret 放进版本库。
  3. check_env.py 从 project.requires-python 读取版本约束，检查项目导入、代理、Redis 和 MySQL，并用 OK/DEGRADED/FAILED 返回可靠退出码。
  4. web/tradingview_zy_chart/app.py:58 调用 create_app()，把 Flask WSGI 应用放进 Tornado WSGIContainer，线程池大小为 10，监听配置的 host 和 9900 端口。
  5. Flask factory 注册蓝图。首页由 pages.py 渲染，认证由 Flask-Login 管理，所有非安全 HTTP 方法由 core.py 统一校验 CSRF。

5.2 TradingView UDF 行情请求

TradingView widget
  → datafeeds/udf/dist/bundle.js
  → GET /tv/config, /tv/symbols, /tv/search, /tv/history
  → udf.py 参数解析与登录校验
  → WebAppServices.get_exchange(Market)
  → get_exchange → ContractedExchange
  → provider.klines / all_stocks / stock_info
  → prepare_klines_for_market
  → 时区、范围、历史请求 tracker
  → {s, t, o, h, l, c, v, update}

firstDataRequest=true 用于完整历史；后续请求才进入 HistoryRequestTracker。Tick 路由在 provider 调用前做代码数量/字节、IP 滑动窗口、固定并发槽和总超时控制。足迹路由使用显示周期与子周期 K 线聚合，并由 10 秒 TTL cache 缓存。

5.3 图表布局、绘图与安全存储

  1. charts.js 创建 TradingView widget，设置 UDF datafeed、charts_storage_url=/tv、client/user namespace 和自定义指标。
  2. 图表自动保存调用 /tv/<version>/charts，模板调用 study_templates，绘图调用 drawings。
  3. storage.py 将协议 user 映射到认证主体，调用 tv_storage.py 做 UTF-8 字节和记录配额校验，再交给 DB 事务。
  4. 数据库用 owner lock、唯一约束和 upsert/更新边界保证同一 namespace 的容量与一致性；绘图保存失败返回稳定错误码和 request_id。

5.4 自选、监控和选股

前端 zixuan.js / alert.js
  → watchlist.py / tasks.py
  → ZiXuan → DB 自选表
  → alert_save / xuangu_task_add 写任务配置
  → 独立 scheduler 读取 DB
  → AlertTasks / XuanguTasks
  → 注册策略 loader
  → SelectionRunner 或 MonitoringRunner
  → BatchRunResult
  → 自选快照原子替换，或 alert_event_save 写事件

策略注册表来自私有配置中的 ALERT_STRATEGIES 和 XUANGU_STRATEGIES。请求不能直接提交任意 module path，loader 只加载服务端注册的类，并在构造前校验允许参数。

5.5 独立 Scheduler

  1. web/tradingview_zy_chart/scheduler.py:28 是独立 CLI，先把 src 和 cl_app 加入路径，再调用 run_scheduler()。
  2. SchedulerLeaderLock 在 DATA_PATH/scheduler/leader.lock 上做跨进程非阻塞锁，第二个实例退出码为 2。
  3. build_scheduler() 惰性导入 APScheduler，创建 AlertTasks(scheduler)，立即 reconcile 一次，再按 5 到 3600 秒范围内的周期重建任务。
  4. 状态 listener 将 job id、名称、更新时间、下一次运行时间和状态写入原子快照；Web 的 /jobs 只读取快照，不在请求进程补启动调度器。

5.6 数据同步与回测

同步入口在 script/crontab/reboot_sync_*_klines.py。它们只读取 JSON 配置并调用 sync_batch.configured_sync_cli()，真正的 Provider 构造和查询发生在 CLI 执行路径。sync_batch.py 为每个 code/frequency 维护配置摘要、attempt、状态、页数和错误，并以 fsync + replace 原子写 checkpoint。

回测入口由调用方、Notebook 或脚本创建 BackTest。BackTestKlines 使用 ExchangeDB 读取指定区间，缓存并按当前时间裁剪多周期 K 线；BackTestTrader 执行 Operation，更新 POSITION、资金、费用和统计。它不经过 Web factory，也不代表真实券商成交。

8. 架构师视角的深度讲解

8.1 设计主线：把变化最大的地方放在边界

市场和第三方 SDK 是变化最大的部分。仓库没有让 Web、策略和回测分别认识每个 SDK，而是把变化集中到 exchange/ adapter，再用 Registry 描述“这个市场有哪些 provider、每个 provider 能做什么”。这使上层依赖稳定的 capability，而不是依赖类上偶然存在的方法。

同样，TradingView 协议和内部领域模型也被分开：udf.py 负责 HTTP 参数和响应形状，web_payloads.py 负责时间/OHLCV，domain.py 负责枚举和错误，策略层收到的是规范化目标。任何一层都不应该把 SDK 原始对象直接传给下一层。

8.2 进程所有权比共享全局更重要

Web worker 的职责是响应请求和持久化配置，scheduler 进程的职责是拥有 APScheduler、执行任务和写状态快照。这个拆分解决了 Flask reloader、多 worker 重复创建 scheduler 和请求线程持有后台任务线程的问题。代价是部署必须同时管理两个进程，并让它们共享同一个 DATA_PATH 和数据库。

8.3 兼容性被显式限制

数据库仍有旧字段和迁移函数，策略存储仍能识别已保存的旧 path，exchange/contracts.py 保留领域类型的兼容 re-export。这些不是“忘记删除”的充分证据，而是迁移层。判断它们能否清掉，必须先证明线上数据已经迁移，并删除对应兼容测试和回滚策略。

8.4 失败策略是 fail-closed

Provider 不可用、能力未声明、Secret 无法解析、交易日历未知、图表 owner 不合法、策略输出不规范时，系统倾向于返回稳定错误或空结果，不猜测成功。实盘下单更是直接关闭。这个策略牺牲了一部分“看起来能跑”的路径，换取不把错误状态写进账本、任务或用户界面。

8.5 当前架构的真实风险

风险原因维护建议
启动路径依赖 sys.path 注入app.py 和 scheduler.py 按脚本相对路径加入 src/web。若要打包或从仓库外以模块运行，应先定义正式 packaging/console script，再移除隐式路径假设。
Scheduler 是部署必需的第二进程Web 不会自动补启动 scheduler，/jobs 只读状态快照。在 Windows/容器/进程管理器中把 Web 和 scheduler 建成两个明确 service，并监控 leader lock 和状态快照。
Provider SDK 仍有外部副作用惰性构造延迟了副作用，但首次请求/任务仍可能连接网络、线程或专有客户端。继续维护 fake/protocol 测试，必要时为每个 Provider 增加 health/readiness 和显式 close。
回测与实时 provider 不同源回测默认读取 ExchangeDB，Web 可读取 TDX、Futu、IB 等。报告中明确数据版本和来源；不要用回测通过替代实时联调。
Registry 与配置仍有 legacy reader为旧 EXCHANGE_* 配置保留兼容读取。统计实际部署后，设计迁移窗口，再删除旧字段和对应测试。
时间/日历是版本化数据现金市场和期货 profile 需要按年份和品种维护，未知年份 fail-closed。把交易所公告、版本、覆盖年份和更新责任纳入发布流程。

9. 后续拓展与修改方法

新增市场或 Provider

  1. 在 domain.py 增加市场枚举或领域类型，并明确是否会影响持久化主键。
  2. 在 market_registry.py 增加完整 MarketSpec：默认代码、周期、TradingView type、payload timezone、session、DB partition 和 provider map。
  3. 实现 Exchange 所需真实方法，在 ProviderSpec.capabilities 只声明已有行为；禁止用继承空桩充数。
  4. 为第三方返回值写边界 normalizer 和故障注入测试，覆盖超时、空数据、乱序、缺字段、重复数据和关闭。
  5. 运行支持矩阵生成器，提交生成的 docs/provider-support-matrix.md，再更新同步 JSON 和前端所需 metadata。
  6. 如果需要秘密，先在 secret_store.py 的 inventory 中分类，配置只存引用。

新增策略

  1. 实现普通 K 线输入的 run(context)，明确选择或监控 purpose。
  2. 在私有 config 的 ALERT_STRATEGIES 或 XUANGU_STRATEGIES 注册 id、路径、默认 kwargs、允许覆盖字段和 JSON schema。
  3. 使用 StrategySignal，不要返回任意 dict、generator 或未经限制的 iterable。
  4. 用对应的 MonitoringRunner/SelectionRunner 测试目标绑定、时区、动作集合和失败隔离。
  5. 需要回测时，显式设计 Signal → Decision → Operation 的桥接；不能把 score 当 position size，也不能把回测 Operation 当 live order。

新增 Web 功能

  1. 先定义 public request/response 和稳定错误码，再在 web_api_validation.py 或领域 contract 中集中解析。
  2. 把路由放入对应 blueprint，通过 get_web_services() 注入 DB、provider、限流器和 logger。
  3. 所有写请求沿用 core 的 CSRF 保护；文件/JSON 输入在 DB 或 SDK 调用之前限制字节、数量和结构。
  4. 前端模板、业务 JS 和 UDF bundle 的 source/产物关系必须同步维护；图表库 bundle 只能走锚点补丁流程。
  5. 为 route 写行为测试和 AST/调用顺序测试；需要真实 DOM 或 MySQL 时放到专门 CI job，不在单元测试中伪装基础设施。

恢复实盘交易的准入条件

不能只恢复一个 adapter 的 order 方法。必须先有持久化 client_order_id、broker order id、状态转移、逐笔 Fill、幂等回调、重启对账、断线恢复和 Provider sandbox 测试；在确认 fill 之前不得更新本地现金、持仓或成功通知。完成这些条件后，才应新增独立的 LIVE_ORDERS capability 和对应 CI/运行文档。

10. 清理审计：可删除内容与证据

清理结论分为四级：确认无活动引用 表示静态证据很强但仍需检查外部部署；高概率过时/需确认 表示存在旧入口或动态使用风险；不建议删除 表示有当前运行、CI 或供应链证据；条件性 表示只有在先归档某组资产后才能删除。

删除原则：“rg 没搜到引用”只证明仓库内静态引用缺失，不能证明外部 cron、Notebook、动态 import、用户书签或生产数据库没有使用。以下建议都不在本次执行。
