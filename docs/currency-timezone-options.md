# B12：数字货币时间约定统一（已选择并实施方案 C）

## 已实施范围

方案 C 已在代码中实施；**没有执行实际数据迁移、登记用户真实数据库或改写历史行**。以下方案比较保留作为设计背景，当前部署只采用 C。

- `currency` / `currency_spot` 运行时统一 aware UTC；naive API/回测起止字符串明确解释为 UTC，Unix 毫秒不经过宿主本地时区。
- schema 第 **5** 项迁移仅创建 `cl_crypto_storage_timezone` 台账，前四项不变。每个数据库、每个 crypto 市场分别锁定一个存储时区；查询、写入、删除、latest 游标使用同一映射。已登记读走只读快路径，首次登记复用 SQLite 跨进程文件锁 / MySQL `GET_LOCK` 并加锁后复查。
- 原生周期历史 DATETIME 钟面值保持不变；读为 UTC，写入 UTC 转登记时区后存 naive。配置与台账冲突报错，删除所有行情也不解除绑定。
- 日线按 UTC 00:00，3h 按 UTC 00:00/03:00/… 合成，不修改输入 DataFrame。数字货币多周期回放按目标桶长度扩充基础窗口（不再固定只取120根），用已到达的基础数据重合成未完成高周期；若缺少桶起点数据则明确拒绝，不能退回带未来 high/volume 的完整高周期行。A/HK/US/期货约定不变。
- 已知自定义周期 `3h`、`10m`、`2m` 使用内部新频率键 `3hC1`、`10mC1`、`2mC1`。公共 API 仍使用原周期名，query/write/delete/latest 全部映射。**旧合成行保留但不再读取，首次新空间可能为空，必须重新同步**；这不是修改旧键，也不是声称旧 OHLCV 已修好。
- 缓存/结果/优化身份为 `crypto-utc-c1`：回测文件、交易状态缓存和配置式同步 checkpoint 使用新文件名；优化 key 加版本。旧产物不删除、不覆盖，旧回测可以历史查看，但禁止续跑、参数优化或信号转交易。内存行情缓存随新实例重建。

### 部署前必须确认

1. 停止所有旧版本服务、同步器和手工导入，备份数据库与旧产物。在副本验证来源和时间锚点；不能从 naive 时间列推断旧时区。
2. 在部署者自己的配置中添加 `CRYPTO_STORAGE_TIMEZONES`（程序兼容未添加此项的旧配置）：

   ```python
   # 以下只是示例，不是自动确认。仅核实来源后填写实际存储约定。
   CRYPTO_STORAGE_TIMEZONES = {
       "currency": "Asia/Shanghai",
       "currency_spot": "UTC",
   }
   ```

   两市场可分别配置；使用明确 IANA 名称，不使用 `local`。若历史真实约定是全年固定偏移，应选择对应固定偏移 IANA 区域，例如 `Etc/GMT-8` 表示 UTC+08:00（Etc/GMT 符号相反），不能用会有 DST 的地区名称替代。`{}` 仅让**整个市场无旧行**时首次绑定 UTC；有未登记旧行情会给出确认配置的操作性错误，不默认上海。首次成功读/写会完成绑定，随后不能随机器迁移或配置变化而更换。
3. 跨 DST 的歧义/不存在钟面值，读取及查询边界均拒绝；即使写入给了 aware UTC，若转换成存储钟面值落在秋季重复小时，仍拒绝，避免两个绝对时刻覆盖同一主键。混合来源、未知时区、歧义旧数据应补充权威原始时间戳或按方案 B 重建，不可随意改台账绕过。
4. 重新运行数字货币同步脚本，补齐 `3h`/`10m`/`2m` 新空间，再运行依赖这些周期的回测。配置式同步入口会在 checkpoint 文件名加 `_crypto-utc-c1`（包括显式 `--checkpoint`），不会信任旧 completed 标记；重复增量仍使用 UTC ISO latest 游标与 upsert。旧 checkpoint 留在原处。
5. 登记仅表示用户声明的历史存储约定，**不证明历史数据来源或合成 OHLCV 正确**。其他自行导入/离线合成的日线或周期，部署者必须核对 Binance 原始时间戳和分组边界；无法证明的序列应在副本重建、验证后再部署。不要把所有旧行统一减 8 小时。
6. 新回测文件名包含 `_crypto-utc-c1`，需要使用返回/日志中的实际路径；旧回测及优化必须重新运行。不要手工给旧文件改名冒充新版本。

### 边界及回滚

- 直接调用 `DB.klines_query` 也返回 UTC-aware crypto 行（已从 ORM session 分离，不会将转换后的日期写回）；非 crypto 保持原行为。latest 为带 `+00:00` 的 ISO 字符串。绕过应用直接 SQL 的外部写入不受保护，部署必须停掉旧写入器。
- SQL 台账不可由应用修改/删除；管理员直接改表不属于支持的迁移方式。首次登记使用锁与唯一主键保证并发配置不能静默覆盖。
- 回滚必须整体恢复备份和旧程序；schema=5 的库不能直接交给 schema=4 程序。运行期间仍保持原生周期的旧存储时区，但合成新空间和结果新命名空间不能被旧程序当作原数据。
- MySQL 验证采用 SQL 编译与模拟，不连接实际 MySQL；Windows 无 `tzset` 时使用会改变 naive `timestamp` / `fromtimestamp` 行为的三宿主模拟，不能仅设置一个无效 TZ 环境变量冒充跨时区验证。


## 修复前根因与完整影响链（背景）

1. `exchange_binance.py` / `exchange_binance_spot.py` 将交易所 Unix 毫秒转换为宿主机本地时区，起始时间字符串也按宿主机解释。
2. `DB.klines_insert`（SQLite/MySQL 两条路径）直接 `replace(tzinfo=None)`，丢掉时区但保留本地钟面值。
3. `ExchangeDB` 对 currency / currency_spot 使用 `market_timezone` 的 UTC，将刚才的钟面值当作 UTC 再读出。
4. `BackTestKlines` 对数字货币仍默认上海，且 naive 字符串通过 `astimezone` 隐式依赖宿主机；查询起止、已加载数据、循环时间可能不一致。
5. 日线合成用输入的小时数判断上海 08:00，输出重新贴上海时区；其他周期按输入时区的午夜锚定。
6. 增量同步把 DB 最新时间返回成**无时区字符串**再传给 provider；缓存、同步 checkpoint、回测保存文件都可能沿用旧语义。

例：真实时刻 `2025-01-01 00:00Z` 在上海机器上写成无时区 `08:00`，读时贴 UTC 后变为 `08:00Z`，实际偏移 +8 小时。这不是“显示成北京时间”，而是表示了另一个时刻。纽约机器产生的偏移还会随夏令时改变。

**不能只在前端改 timezone、只把日线切成 UTC、或把所有历史行统一减 8 小时。** 不知道历史写入环境的数据不能从无时区日期单独推断回来；同表混用多个环境时必须核对可信时间锚点或重拉。

## 所有方案共同的正确性要求

- 区分三件事：绝对时刻、交易所 bar 起点、用户显示时区。
- 数字货币运行时采用 aware UTC；无时区配置字符串有显式约定，不读取操作系统默认时区。
- Binance 日线按 UTC 00:00 分组，上海展示为 08:00；分钟与小时周期按交易所边界锚定。**3h 周期必须重算分组，不能仅平移日期标签**。
- 起止查询、latest-date 增量游标、删除键、去重主键、同步 checkpoint 必须一起切换。
- 迁移前停止写入并备份；先 dry-run 出清单与冲突，不能直接 UPDATE 然后遇主键冲突才想办法。
- 不修改 A 股/港股/期货/美股时间约定，除非选择最后的大范围方案。

## 方案 A：数字货币专用 UTC 边界 + 原表离线迁移（推荐：数据来源可确认时）

### 实施步骤

1. 增加数字货币时间转换 helper：aware 输入转 UTC；naive 入参按明确 UTC 约定解释，旧 API 入口提供一次明确转换而非猜测。
2. 两个 Binance provider 输出 UTC；`ExchangeDB` 查询/读取、`BackTestKlines` 参数/游标采用同一约定；日线和 3h 合成按 UTC 锚定。
3. DB 只对 currency/currency_spot 在写入前转 UTC，再存 UTC-naive DATETIME；查询边界也转同样存储形式。其他市场保持原状。
4. 迁移工具要求用户声明旧数据来源时区，按市场/代码/频率扫描；生成“旧键→新键”映射、冲突、缺口与抽样校验报告。
5. 停写；备份；对每张表使用影子表或两阶段改键（避免逐行平移撞上已有主键）；验证后切换。记录存储语义版本到独立数据迁移台账，**不是每次 import 执行**。
6. 重建无法证明锚点正确的合成周期，废弃旧数字货币缓存与同步 checkpoint，保留归档；旧回测结果仍可查看但不与新口径混合比较，需重跑。

### 范围/影响

- 约 8–12 处活动模块/入口及专项测试：两个 provider、DB、ExchangeDB、BackTestKlines、converter、同步/游标、迁移命令。
- 已有 crypto DB 的时间主键改变，需要短暂停写。新安装空库直接用新约定。
- Web 的 Unix 时间变为正确值；以往偏移的图表/结果可能变化，这是修正而非保持错误兼容。

**优点**：只影响数字货币；不长期维护双格式；现有 DATETIME 表结构可保留；与 Web 已规定的 UTC 一致。

**缺点**：必须确认旧数据时区；混合来源不能安全自动迁移；需要备份/停写和旧缓存重建。

## 方案 B：新建 UTC 版本行情存储，分批重建后切换（推荐：历史来源不清或不能一次停机时）

### 实施步骤

1. 运行时同 A 统一 UTC，但新建 crypto v2 表/独立 schema 或命名空间，与原表完全隔离。
2. 给每个序列记录 schema/timezone/source/migration-status。读路由由显式版本决定，**不把 v1、v2 时间混在同一条查询中**。
3. 新同步只写 v2。历史来源明确的序列可转换导入；来源不明确的，按交易所时间戳重新下载到 v2；原始导入数据无权威来源时保留 v1、标记待处理。
4. 按代码/频率比较数量、时间范围、重复/缺口、随机 OHLCV 与日线边界；通过后原子切换该序列。同步游标和缓存 key 包含 v2 标识。
5. 回测要求所有请求频率来自同一版本；数据未齐时明确失败，不拼接两种口径。
6. 观察期保留 v1 只读，一键把路由切回可回滚；最终用户确认后再清理旧库。

### 范围/影响

- 约 12–18 处模块/入口及测试；比 A 多存储路由、数据版本台账、迁移/下载工具与状态报告。
- 较长期间占用约两份 crypto 数据；重新下载受供应商历史深度、限流和退市品种可得性限制。
- 同市场只读功能可保留，但未迁移序列不应无声地返回旧格式。

**优点**：原表不动、回滚清晰；混合来源可以重建而不是猜偏移；可分批上线，对大库更稳妥。

**缺点**：实现与运维最多；双库占空间；重拉不一定能补齐历史；过渡期必须严格控制跨版本读取。

## 方案 C：显式固定旧存储时区，运行时 UTC，不改历史主键

### 实施步骤

1. 为数字货币存储登记明确时区，例如 `Asia/Shanghai`，而不是 `local`；只允许确认来源一致的旧库采用。
2. provider、合成、回测统一 aware UTC；DB 写入时 UTC→存储时区→naive，读取时 naive→登记时区→UTC。
3. 查询、删除和 latest-date 游标也通过同一转换层；增量同步传 UTC aware/带偏移的 ISO 字符串，不能直接传库内钟面值。
4. 存储时区写入持久台账并锁定，不能随配置/操作系统静默改变；跨夏令时来源遇歧义/不存在时间直接拒绝，要求补证或走 B 重建。
5. 旧缓存/回测合成依然需要失效或重算，不能因未改 DB 主键而沿用错误结果。

### 范围/影响

- 约 7–10 处模块/入口及测试；不批量更新原数据，主要增加显式存储边界。
- 确认只在上海机器写入且从无混入其他来源时，可以少停机修正读取。

**优点**：迁移成本最低；不修改历史键；可以作为未来 A/B 的过渡。

**缺点**：长期保留“存储非UTC、运行时UTC”两套约定；所有绕过 ExchangeDB 的 DB 调用都必须受控；混合来源和夏令时重复钟面值仍无法可靠恢复，不能当作通用无迁移方案。

## 方案 D：全市场存储统一 UTC

把 A/B 的范围扩展到全部供应商、市场、导入导出、日周月线锚点和交易日历。

**优点**：长期内部时间模型统一，扩展新市场更明确。

**缺点**：影响几十处代码及全部历史 K 线；股票收盘标签、期货夜盘交易日、纽约夏令时、周月线都需单独定义，不能简单 tz_convert。超出 B12，回归与迁移风险最大，当前不推荐。

## 对比与建议

| 方案 | 改旧数据 | 停写要求 | 长期复杂度 | 混合来源 | 推荐场景 |
|---|---|---|---|---|---|
| A 原表 UTC 迁移 | 是 | 切换时停写 | 低 | 需先识别，不能猜 | 来源明确、可备份停写 |
| B v2 重建切换 | 旧表不改 | 按序列切换 | 过渡期高 | 可重拉重建 | 来源不清、大库、要回滚 |
| C 显式旧存储时区 | 否 | 配置切换时短暂停写 | 中 | 不支持混杂 | 确认单一时区的小型旧库 |
| D 全市场 UTC | 全部 | 最大 | 完成后较统一 | 仍需识别 | 单独架构项目 |

当前已选择 C，程序不做历史主键迁移。部署前仍须**只读数据来源盘点**：确认有哪些 crypto 表、哪台主机写入、是否混合导入、是否能重拉；不满足 C 前提时停止，不自动退回猜测时区。

## 统一验收与回滚门槛

1. UTC、上海、纽约三个宿主时区运行同一输入，Unix 时间与 OHLCV 完全相同。
2. 覆盖日界、3h/4h 边界、闰日、纽约夏令时切换、空数据、重复主键和无时区输入拒绝/约定。
3. SQLite/MySQL 写→读→同一 Unix 时间；限界查询与 latest-date 增量续传无缺口、无重复。
4. Binance 原生日线与小周期合成日线比对；多周期回测不得引入未来数据。
5. 分页中断/迁移中断可继续；第二次执行不得再偏移；混合来源不得自动减 8 小时。
6. 先在数据副本运行；保留版本路由/完整备份和缓存副本；切换失败恢复旧读写程序与旧数据库，不能把新程序接回未标记的旧格式。
