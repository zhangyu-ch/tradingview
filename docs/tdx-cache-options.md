# B5：六个 TDX 适配器统一缓存修复方案（已实施 B + M2）

适用：`exchange_tdx.py`（A 股）、`exchange_tdx_hk.py`、`exchange_tdx_us.py`、`exchange_tdx_futures.py`、`exchange_tdx_fx.py`、`exchange_tdx_ny_futures.py`。

用户已选择并实施 **B：共享纯拼接器 + 统一 key**，采用 **M2：新原始缓存版本**。保留既有 B18 网络预算/失败语义和 B19 生命周期修复；候选方案与原问题说明留作决策依据。

## 实施结果

- `exchange/tdx_cache.py` 提供 `tdx_cache_key` 与 `refresh_tdx_window`，无 SDK、业务 DB 或文件读写依赖；六适配器保留 SDK 调用、页归一化、时区、复权及周期转换。
- key 为 `tdx_raw_v2_` 加 `(market, 原始 code, frequency)` JSON 的 SHA-256；同一 key 用于读写，同时避免 FileCacheDB 文件名将点替换为下划线造成碰撞。格式版本与 sidecar 版本独立。
- 分页前固定原缓存最大 `date`，从偏移 0 每次递增 700，直到新窗口覆盖该时间；不再把新增第一页的尾部当成衔接目标。所有输出按 `date` 升序且唯一，新下载覆盖旧缓存，后下载行覆盖先下载同时间行。
- `None` 与零行缓存（包括 FileCacheDB 去掉唯一未完成 bar）均走全量分支。第一页正常空响应返回空表且不写缓存；后续空页终止；正常取满或空页仍未接上时，仅保留新下载窗口并记录 warning，不跨缺口拼接旧缓存。
- 传输或归一化异常向上传播；本次原始拉取不写部分结果。超出 B18 时限仍抛异常，不将超时降格成短历史成功。共享 helper 不增加重试、连接或预算。
- 页数保留 A/HK/国内期货/纽约期货 8、美股 5、外汇 10、A 股周线 12；每页 700。
- A 股 M2 缓存在 13:00→11:30 返回修正前保存原始日期，避免第二次调用将修正后的缓存日期与 SDK 原始日期比较；复权和输出时区仍只影响返回数据。国内/纽约期货沿用适配器自己的夜盘归一化日期。
- 不回读、迁移、重命名或主动删除旧 key 文件；首次访问重新拉取窗口。**FileCacheDB 原有按市场概率触发的 15 天维护策略未改变**，因此不是旧文件永久保留承诺；B5 未新增任何清理调用。
- 连续窗口指连续 SDK 分页获取的窗口，不推测交易日历、不补造 bar，也不修复上游自身缺失的行情。完整原始数据已成功后发生的复权失败仍遵循原适配器行为，不回滚已成功的原始缓存。

### 离线验收

`tests/test_b5_tdx_cache.py` 覆盖共享 helper 与六适配器真实方法的 fake SDK 行为：跨超过两页衔接、反序/重复时间、新数据覆盖、无衔接、首/后空页、仅未完成 bar、读写 key 一致、版本/市场/周期隔离、部分请求失败不写、三次重试与共享 12 秒预算、夜盘及 A 股原始/返回日期隔离。SDK、私有配置和业务 DB 均不加载；FileCacheDB 实际方法仅在临时目录执行。

原 B18 测试仅补充两个共享函数的 AST namespace 注入，保留原断言。扩展回归包括 ME12、ME14、NX20、LO02 与 FileCacheDB 安全测试。

## 一、六者共有的正确性要求（实施前问题基线）

1. 同一个 `(市场, 原始代码, 周期, 缓存格式版本)` 必须得到同一个读写 key。修复前期货读 `code`、写 `v1_code`；其他五个读写一致。
2. 增量连接的基准必须在分页前固定为缓存最后时间 `cache_end`。不能用每次拼接后的最后一行判断；修复前六者都有该问题。
3. 页内和页间均按时间排序、按时间去重，新页覆盖缓存中同一时间的旧 bar；不能假设服务端页序固定。
4. 服务端空页必须安全终止，不再访问 `datetime` 或 `iloc[0]`；需区分「服务端正常空页」与「请求失败」，网络失败由 B18 抛异常，不写入半成品。
5. 超过页数/总时限仍没有接上缓存，不得返回看似连续的有洞历史。建议丢弃本次结果中的旧缓存片段，仅返回本次真实获取的连续窗口；写入时也只写这个窗口，保留明确日志。
6. 保留 FileCacheDB 的原子 CSV/metadata 写入、SHA 校验和 `last_row_complete` 语义。其默认读取会去掉最后一根未完成 bar；只有一行时读取结果可能是空表，也必须走首次全量分支。
7. key 版本是「缓存结构/时间处理语义版本」，不是 `FileCacheDB` 的 sidecar 格式版本，两者不能混为一谈。
8. 保留六市场自己的转换：A 股复权与盘中时间修正、期货夜盘、纽约期货夜盘、美股 DST、各自成交量来源以及特殊周期合成。共享逻辑只负责原始页的衔接，不重写市场公式。

当前默认页数：A 股/港股/国内期货/纽约期货为 8，美股为 5，外汇为 10；A 股周线会使用 12 页。每页 700 根。统一算法**不等于把各市场页数强改成一样**。

## 二、候选方案

| 方案 | 实施内容 | 优点 | 缺点 / 影响范围 |
|---|---|---|---|
| A：六处最小补丁 | 每个适配器保留现有分页循环，统一调用一个 key 函数；分别固定 `cache_end`、空页退出、断档处理 | 最容易逐文件核对；一次改动较小；市场细节不变 | 六份循环仍会再次分叉；每处修复都要重复；六套边界测试不能省 |
| **B：共享纯拼接器 + 统一 key（推荐）** | 新增一个无 SDK/DB 依赖的分页拼接 helper；六适配器只传 `缓存/取页函数/页转换函数/页数`，调用同一个读写 key 函数 | 一处解决重复时间、空页、衔接和断档；纯函数容易造数据回归；不触碰生命周期、复权与时区 | 相比 A 多一个模块、需要把六种日期转换作为窄回调；首次改造要验证六个市场 |
| C：统一 TDX 行情基类/完整管线 | 把连接、分页、缓存、转换、复权和输出都收进公共基类，适配器只配参数 | 重复代码最少，后续新增同类市场方便 | 改动最大；不同市场的行为容易被错误统一；会和本轮 B18、既有 NX20/LO02/ME12 的生命周期边界重叠，不适合只修 B5 |
| D：停用 CSV 增量缓存，每次全量获取最近 N 页 | 六个适配器不读写该缓存，只返回本次窗口 | 简单、彻底消除错误拼接；无旧缓存迁移 | 请求量持续升高；历史窗口变短；离线容错下降；期货现在已近似如此，其他五市场会明显退化；不推荐长期使用 |

推荐 **B**。它不是把六个交易所揉成一个大类：共同部分只回答「缓存与新页能否无缝衔接，最终保留哪些原始行」。

### 方案 B 的具体边界

- `tdx_cache_key(market, code, frequency)`：返回原始缓存使用的规范代码/key；不要在 12 处手写前缀。
- `refresh_tdx_window(cached, fetch_page, normalize_page, max_pages)`：只操作 DataFrame 和回调；固定 `cache_end`，累计新页，接上即停；空页/取满仍未接上时按统一规则只保留新窗口。
- 适配器负责打开 B18 的有界连接、读写 FileCacheDB、构造 `fetch_page`，以及返回后的复权/时区/周期转换。
- 网络异常直接向上传播：helper 不把它当空页、不清空正常旧缓存，也不写一半成功的结果。
- 不新增后台任务、线程或数据库表；不把文件清理塞进每一页。

## 三、缓存兼容策略（与 A/B/C 可独立组合）

### M1：保留旧 key，只修国内期货（最少重拉）

- 其他五市场沿用当前 key，国内期货读写统一 `v1_code`。
- 优点：现有文件能立即复用，首次网络量最小。
- 缺点：其他市场旧文件里可能已经有历史缺口。新算法只能防止继续造洞，不能证明旧缓存内部完整；若选此策略，需一次独立缓存审计/清理或接受这个限制。

### M2：六市场统一切到新原始缓存版本（推荐搭配 B）

- 六者使用新版本 key（例如 `tdx_raw_v2_` + 原代码），不回退读取旧版本。
- 优点：从可信的新窗口开始，既解决期货 key 错误，也隔离其他五者已经可能被错误拼接污染的缓存；不移动历史业务 DB 数据。
- 代价：每个代码/周期第一次打开要重拉 N 页；旧文件暂时占用磁盘。
- 清理：新版本正常运行后，提供列出旧文件的 dry-run 命令或等待既有 15 天清理策略。**不直接批量删除用户行情数据。** 若旧文件清理仅在命中路径触发，应让清理由已成功的缓存读写操作按市场触发，并且保留现有概率/频率限制。
- 回退：代码回退时旧缓存仍在；新版本文件不被旧逻辑误读。

### M3：旧文件就地迁移/重命名

- 优点：节省首次下载。
- 缺点：CSV 和 sidecar 要一起校验、迁移；就地改名不能修复历史缺口；如果迁移时间语义，还会与 B12 时区方案耦合。对可再生成缓存不值得，通常不选。

## 四、断档策略的可选差异

- **默认推荐：只返回连续的新窗口**。请求数和 B18 时限不变；旧的更早历史暂不可见，但不会把洞当成连续交易历史。
- 扩大页数直到接上：保留更多历史，但会显著增大网络与延迟，仍应有绝对页数/时间上限；不能无限追赶。
- 检测到断档就报明确错误：数据使用方不会误用短历史，但图表可能完全无数据，用户体验差。

## 五、影响和验收清单

- 覆盖六个适配器，不改 market registry、策略、回测、Web URL 或数据源选择。
- 可能改变的可见结果：之前错误拼出的长历史改成较短但连续的窗口；期货缓存命中后请求量下降；各市场热缓存通常只拉最新一页。
- 不能只断言源码字符串。用参数化行为测试覆盖：首次无缓存、缓存只含未完成 bar、同一 bar 被更新、跨多页才衔接、完全追不上、第一页空、后续页空、反序页、重复页、网络中断、无效 CSV、元数据不一致、六个市场的日期转换。
- 单独验证美股 DST、国内/纽约期货夜盘、A 股周线/复权，防止共享 helper 改变原有行情语义。
- 回归至少包含 `test_me12_tdx_contracts.py`、`test_nx20_tdx_bounded_retry.py`、`test_lo02_shared_market_workflows.py`、FileCacheDB 原子/sidecar/完整 bar 相关测试和本轮 B18 测试。

## 六、本轮 B18/B19 的边界说明

- 已改：六 TDX 的原始 K 线请求重试上限 3 次，单次行情拉取共享 12 秒 socket 预算，关闭 SDK 内部自动重试；连接/握手/多次 partial recv 和故障节点重新选择都在预算内。A 股除权信息另有一个 12 秒有界请求；不把两个预算误称为整条 `klines` 最多 12 秒。
- 已改：Binance spot/futures 按 `NetworkError` 重试，分页共享请求预算；TQ 只等待一次 5 秒，超时明确报不可用；IB 空历史直接返回空表。
- 已改：移除 13 个适配器单例装饰器，由 `get_exchange` 工厂缓存拥有实例；两个市场使用 Futu 时各有实例，切换其中一个不会关闭另一个。
- 已改：港股/美股 AkShare 复权因子只把真实 HTTP 请求交给仓库现有 `DeadlineCaller`（两者共享 2 个槽），与该次原始 K 线共用剩余 12 秒预算；超时/容量耗尽抛可重试不可用错误，原始原因保留。CSV 保存和复权公式仍在调用线程，超时的后台结果不会继续写文件。
- 边界：AkShare/CCXT 不响应自身超时时，Python 不能强杀其线程；超时工作会继续占槽直到真正结束，两槽都被占时新请求立即失败，不会无限新建线程。Binance 另有共享 2 槽的独立边界，避免复权源阻塞数字货币行情。长时间卡死的 SDK 最后可能需要重启进程。
- B5 本次已改：统一新版本 key、固定缓存尾部衔接、正常空页/断档策略；未实施旧文件迁移或新增清理。
- B12 由独立时区边界改动处理，不属于本共享 TDX 模块；账户/委托等非 K 线方法的重试策略未改。实盘下单禁用约束不变。
